# Manifest specification

The manifest answers one question: what would I have to hold fixed to get this
number again? Everything else is optional.

## Schema

```json
{
  "run_id": "a3f9c1d2e8b40571",
  "created_utc": "2026-07-25T14:03:11Z",
  "tags": {"arm": "cot", "comparison": "prompt_ablation", "group": "seed_sweep"},

  "code": {
    "git_commit": "9f2a1c4",
    "git_dirty": false,
    "git_remote": "git@github.com:user/cpath-triage.git",
    "entrypoint": "src/infer.py"
  },

  "config": {
    "path": "configs/base.yaml",
    "overlays": ["configs/arms/cot.yaml"],
```

## Hashing rules

**`run_id`** = first 16 hex chars of `sha256(resolved_config_canonical_json + git_commit)`.

Canonical JSON means: keys sorted, no insignificant whitespace, floats
serialized with `repr`. Without canonicalization, reordering a YAML block
changes the id and destroys the collision property that makes the id useful.

Fields deliberately excluded from the id: timestamps, output paths, `slurm_job_id`,
tags. Two runs of the same thing on different days should collide. Fields
deliberately included: seed, because a different seed is a different run.

**`resolved_sha256`** is over the merged config after overlays are applied, not
over the base file. The merged config is what actually ran.

**`split_sha256`** is over the split file contents. If splits are generated
rather than stored, store them once and hash the stored file. A split
regenerated by a function with a seed is only as stable as that function, and
library sampling behavior changes across versions.

**`template_sha256`** is over the raw template string with trailing whitespace
preserved. Prompt behavior is sensitive to whitespace and a stripped template
is a different template.

## Handling unknown fields

Do not invent values. Use `null` with a `note`:

```json
"revision": null,
"notes": {"revision": "endpoint did not report a revision string; recorded served-model-name only"}
```

A null with an explanation is honest and reviewable. A plausible guess is
undetectable and wrong.

## What to record for a hosted endpoint

When inference runs against a shared server rather than an in-process model,
record the server's identity as well as the model's:

- `endpoint_job_id`: which server process served this run
- `served_model_name`: the string the endpoint reports
- server start time, if available

A server restart between two arms of a comparison changes the weights loaded,
the runtime, and possibly the tokenizer. If the two arms of a comparison have
different `endpoint_job_id` values, that is worth knowing before attributing a
difference to the intervention.

## Determinism, stated honestly

Three cases:

1. **Deterministic**: fixed seed, single-threaded reduction, no atomics. Rare in
   practice on GPU. Claim it only if a repeat run produced bitwise identical
   outputs, and record that check.
2. **Seeded but not bitwise reproducible**: the usual case for GPU training.
   Record the seed and report run-to-run variation from at least two seeds.
3. **Nondeterministic by construction**: LLM serving with continuous batching.
   The batch a request lands in affects the result. Record it as such and
   measure the noise floor by rerunning one arm unchanged.

Case 3 matters for ablations: if the run-to-run difference of an unchanged arm
is the same size as the between-arm difference, the ablation has measured noise.
Report both numbers together. The noise floor measurement costs one extra run
and preempts the most damaging review comment available on this class of paper.

## Minimum viable manifest

If adopting this incrementally, these five fields recover most of the value:

1. `config.resolved_sha256`
2. `code.git_commit` and `code.git_dirty`
3. `data.split_sha256`
4. `model.id` + `model.revision`
5. `prompt.template_sha256`

Add the rest as the project grows. A partial manifest that is actually written
beats a complete schema that is skipped because it is tedious.
