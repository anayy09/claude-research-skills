## Local additions

Everything above this heading mirrors `blader/humanizer`. This section is kept in `local-additions.md` and re-attached by `scripts/sync_upstream.py`, so edit it there. Where it disagrees with the text above, this section wins.

### Facts in text that goes out under the user's name

The workflow above allows adding a specific detail you know to be true. That holds for general prose. In an email, cover letter, CV, statement of purpose, biography, social post, form answer, manuscript, or response letter, a detail comes only from the text being edited, from the user, or from the project's own files (`AUTHORS.yaml`, the CV, a results file, a memory note). Do not supply a result, date, title, affiliation, credential, or name from general knowledge. If the sentence needs a detail you do not have, ask for it or write the plainer sentence.

### Research manuscripts

When the text is a manuscript, thesis chapter, or response letter, do the work without comment on which skill applies. Run `manuscript-writing`'s `prose_lint.py` and follow that skill's rules, which are the manuscript form of the patterns above, then use this file for anything the lint does not cover (§2 closers, §26 re-explaining). The user often names both skills in one request. That is an instruction to apply both passes, and it needs no reply about scope.

### Messages: email, chat replies, posts, comment replies

These come from corrections the user has made to drafted messages.

- **Open with the point in the user's own register.** "I had the chance to run the open house with Divya" is how the user starts a post. A scene-setting first line is not.
- **A reference message is context, not a template.** When the user shares someone else's post or email for background, take the facts from it and none of its sentences, structure, or anecdotes.
- **Name work by its topic, not its rank.** "My paper on federated continual learning", not "my first-author Scientific Reports paper". The CV carries authorship and venue. The same goes for a CV entry: no "(first author)" or "sole author" tags unless the user asks.
- **Match the length and style of what is being answered.** A reply to a one-line comment is one to three sentences in the commenter's register. "It is just for reply's sake" means the shortest true answer.
- **Check every time reference against the send date.** "In the next week or two" is wrong when the user is away next week. Ask when the message will be sent if it matters.
- **Do not narrate what the reader can see.** No "as you can see in my CV", no summary of the attached file, no account of how the work was done unless it was asked for.
- **Leave out what the user did not decide to say.** A compliment someone paid, an internal difficulty, a limitation nobody raised: these stay out unless the user put them in.
- **Deliver it ready to paste.** Plain text with real line breaks, no Markdown markers, the signature as plain lines. For Outlook, say so if a rich-text copy (an `.html` file opened in a browser) is the better route.
- **Give Celsius beside Fahrenheit and write dates in full** when the message or note is for the user.
